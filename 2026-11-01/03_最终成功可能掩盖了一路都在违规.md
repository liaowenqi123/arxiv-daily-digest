# 2026-10-29 · 最终成功,可能掩盖了一路都在违规|Prefix Executability: Evaluating Tool-Using Agents Beyond Final Success

> arXiv:2610.40444 · 提交:2026-10-29 · Amir H. Rezaeian, Weiyi Sun, Yassine Benajiba, Dan Roth(Oracle AI)· NeurIPS 2026 Evaluations & Datasets
> 一句话:工具调用智能体的"最终成功率"会把"中途已经不可执行、靠事后修补蒙对"的轨迹算成成功;改测"每一步前缀是否可执行",排名会翻。

## 〇、人话版(先看这个)

- **输入**:一个工具调用智能体在任务中生成的**动作序列**(调用哪个工具、什么参数),以及工具 schema、状态前置条件、跨步依赖。
- **输出**:一组**前缀可执行性**指标:PEC(前缀可执行曲线)、FED(首次错误深度)、TER(轨迹可执行率)、AUC-PEC、RR(恢复率)。
- **任务**:**评测协议**,不是新智能体。
- **老问题**:工具调用基准大多只看**最终是否成功**。但最终成功可以来自:① 一路都对;② 中途违规、后来补回来;③ 绕过了任务本来要求的流程。
- **它改了什么**:把"轨迹的每一个前缀是否仍可执行"作为一等公民来测。可执行性不要求匹配某条标准答案,只要在工具语义与当前状态下能跑通即可。
- **凭什么更好**:排名会**分叉**。BFCL 上,GPT-5.4 的 Plan-Cond. ReAct 最终成功率 **0.94**(最高),但 TER 只有 **0.47**、AUC-PEC **0.54**;Dual-Loop 最终也是 **0.94**,TER **0.94**、AUC-PEC **0.96**。也就是说:同样的"成功",一个是一路可执行,一个是靠事后恢复——旧指标看不出区别。
- **代价**:需要工具 schema / 状态语义(评测环境要有);"可执行"不等于"符合用户意图";样例是分层抽样(200/数据集)。
- **类比**:两个人考试都得了 90 分。一个每题步骤都对;另一个前三题写错、靠橡皮擦改回来,还有些步骤其实是抄旁边的。只看分数,他们是同一种学生。

## 一、它在跟什么较劲

工具调用智能体的评测,长期被"最终成功率"统治。

但这类任务的成功**不是一次性判断**,而是一条轨迹:

- 先查记录,拿到 id;
- 用 id 去更新/支付/通知;
- 中间任何一步引用了过期 id、跳过了前置条件、或者顺序错了,后面的调用就可能**语法合法但不可执行**。

而智能体很擅长"事后补救":一个错误调用之后,它可能再发一个修复调用,最终把状态改对。

**于是最终成功=1,但轨迹在中途就已经坏了。** 对真实系统来说,这个区别是致命的:一条在支付前就发了通知的轨迹,即使最后金额对了,业务上已经出错。

## 二、核心思想(机制层)

### 1. 可执行前缀:一个不需要标准答案的定义

对一条轨迹的每个前缀,检查它是否在**工具 schema + 状态前置条件 + 跨步依赖**下仍然可执行。

- 不要求"和参考轨迹一样";
- 允许多条合法路径;
- 但每一步都必须在语义上跑得通。

### 2. 五个指标,分别回答不同问题

| 指标 | 回答什么 |
|---|---|
| PEC | 随步数变化,前缀仍可执行的比例 |
| FED | 第一次出现不可执行的深度(越深越好) |
| TER | 整条轨迹是否全程可执行 |
| AUC-PEC | 对 horizon 归一化的整体可执行性 |
| RR | 出错之后,有多少比例被恢复 |

**关键**:这些指标不是"更严格的成功率",而是**不同的问题**。一个智能体可以成功率高但 TER 低(靠恢复),也可以 TER 高但成功率低(不敢行动)。

### 3. 为什么"计划条件化"会在这里翻车

Plan-Cond. ReAct 先写一个计划、再按计划执行。它的最终成功率很高——因为计划让它看起来很有条理。

但它的**前缀可执行性很差**:计划是在没有验证的情况下生成的,执行时经常引用还不存在的东西。于是 TER 低、FED 浅,靠后面的恢复把最终状态救回来。

**这是一个典型的"过程坏、结果好"**。

## 三、为什么反直觉 / 优雅在哪

- **反直觉**:让智能体"先做计划"通常被认为是好实践;在可执行性这个轴上是**负分**。
- **更反直觉**:同样的最终成功率(0.94 vs 0.94),两个系统的可靠性可以差一倍(TER 0.47 vs 0.94)。
- **优雅**:没有训练新模型。只换了一个评测单位——从"整条轨迹成不成"换成"每个前缀成不成"。
- **判据**:如果加入前缀指标后,所有系统的排名与最终成功率完全一致,那这个指标就没提供新信息。

## 四、关键证据

BFCL(GPT-5.4,分层 200 例):

| 方法 | 最终成功 | TER | AUC-PEC | 平均 FED |
|---|---|---|---|---|
| ReAct | 0.61 | 0.69 | 0.83 | 5.61 |
| Prompt Planning | 0.78 | 0.78 | 0.85 | 5.72 |
| Plan-Cond. ReAct | **0.94** | **0.47** | **0.54** | 4.11 |
| Dual-Loop | **0.94** | **0.94** | **0.96** | 6.41 |

- 同样的最终成功率,TER 差 **0.47**,AUC-PEC 差 **0.42**。
- 在更弱的模型上差距更大(Llama-4 Maverick:TER 0.05 vs 0.88)。
- 验证性干预:执行前显式检查计划,能提高前缀存活率,同时保持有竞争力的最终成功。

## 五、边界与可疑处

- 需要工具 schema 与状态语义;开放域任务难以定义"可执行"。
- "可执行"是**技术正确**,不等于"符合用户意图"或"业务正确"。
- 抽样 200 例/数据集;虽然给了 bootstrap 置信区间,但覆盖有限。
- 只在三个基准上做;不同工具生态下结论可能变。
- 我未核对附录里的完整协议与实现。

## 六、对我们有什么用

- **可直接借(评测思想)**:我们的回测/交易智能体也会犯"过程坏、结果好"的错——比如在错误的时点下单、靠后续调仓救回来,最终收益看起来不错。**应该测"每个决策前缀是否在当时的信息集下可执行/可解释"**,而不只看最终收益。
- **可直接借(指标)**:定义"首次错误深度"(策略从第几步开始偏离可执行集)和"恢复率"(偏离后救回来的比例)。这两个数比夏普比率更能诊断系统。
- **值得做的小实验**:在我们的策略回测里,记录每一步的"当时是否满足约束"(仓位上限、可用资金、涨跌停),统计 FED 与 TER。如果 TER 很低但收益不错,说明策略在靠运气补救。
- **只能当反面教材**:别用"最终指标好"证明"系统可靠"——它可能只是在违规之后成功补救。

## 七、值得抄的一句话

> "Terminal outcomes can obscure whether the intermediate tool-call trajectory was executable."

> 终端结果会掩盖中间的工具调用轨迹是否真的可执行。
