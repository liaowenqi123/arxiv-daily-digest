# 2026-08-17 · 记忆不是越大越好,要"先小后大"|Proteus: Incremental Memory Activation for Long-Context Sequence Modeling

> arXiv:2608.16844 · 提交:2026-08-17 · Reza Bayat, Ali Behrouz, Vahab Mirrokni, Aaron Courville(Mila / Google Research)
> 一句话:固定大小的记忆会被开头几个 token 占满;先只给一小块、逼它压缩,再逐步解锁新块,长上下文反而更好。

## 〇、人话版(先看这个)

- **输入**:一段长 token 序列(语言建模)。
- **输出**:下一个 token;机制上改的是"记忆容量怎么用"——不是模型输出形式变化。
- **任务**:**序列建模 / 长上下文**(记忆架构),不是预测、不是分类。
- **老问题**:用固定大小隐状态压缩上下文的模型(RNN、线性注意力、SSM),**写入是"边读边写"的**。开头 token 到来时状态几乎是空的,没人跟它抢容量,于是它**不需要压缩**,可以霸占大量自由度;后面的 token 只能往剩下的缝里塞,不断覆盖前面的内容。结果:记忆偏向开头,长上下文一长就崩。
- **它改了什么**:把"容量"从常数改成**随上下文增长的日程**。早期**故意只开一小块**(制造瓶颈,逼模型压缩开头),随着上下文变长**逐块解锁**新容量(给后文腾地方,减少覆盖)。
- **凭什么更好**:16K 上下文的 NIAH 上,Titans 的 S-NIAH-3 从 **21.4 → 29.8**、S-NIAH-2 从 **69.4 → 74.2**;Comba 的 S-NIAH-2 从 **13.4 → 21.2**。常识推理平均分 +0.7~0.8 个百分点,LongBench 平均 +0.2~0.9。**增益随上下文变长而变大**,短上下文(模型已饱和)几乎不变。
- **代价**:要改架构(块状激活 + 门控);只在 760M / 1.3B 上验证;调度在 8K 训练窗口内就走完了,16K 的增益来自"压缩得更干净",不是无限扩容。
- **类比**:搬家装箱。先只给小箱子,逼你把东西压缩、分类、扔掉;装满了再给新箱子。如果一开始就给一个大仓库,你会把什么都平铺进去,等真正要用的东西来了,反而没地方放。

**作者核查**:Aaron Courville(Mila 教授,深度学习教科书作者之一)、Vahab Mirrokni(Google Research 副总裁/研究员)、Ali Behrouz(Google,记忆架构方向高产)都是圈内可查的资深研究者;一作 Reza Bayat 是 Mila 学生。可信度:**高**。

## 一、它在跟什么较劲

长上下文的两条路:

1. **注意力**:无损,但显存/计算随长度涨;
2. **固定大小记忆**(RNN/SSM/线性注意力):线性成本,但把无限上下文压进有限状态,必然丢东西。

第 2 条路的传统改法是"让记忆更强":更好的初始化、更好的更新规则、更大的状态。这篇换了个问法:

> 问题也许不在"怎么写",而在"**什么时候写**"。

## 二、核心思想(机制层)

### 1. 病根:早期 token 没有压缩压力

在线写入的记忆里,第 1 个 token 面对的是空状态——它想占多少自由度就占多少,因为没人竞争。等第 $10^5$ 个 token 到来时,状态已经满了,它只能覆盖已有内容。

这不是"容量不够",是**容量分配的时间结构错了**:开头被过度表示,结尾被过度覆盖。

### 2. 药方:把容量做成时间的函数

- 把记忆状态切成若干块;
- 第 $t$ 步只有前 $b(t)$ 块**可读可写**,其余块**锁死**;
- $b(t)$ 随上下文位置**阶梯式增长**,在训练窗口内走完。

两个效果同时发生:

- **早期瓶颈** → 逼模型把开头压缩成摘要,而不是逐字存;
- **后期解锁** → 新信息有干净的块可写,不与旧内容互相干扰。

**如果只能记住一张图**:一条阶梯上升的"可用块数"曲线,叠在一条下降的"每块写入冲突"曲线上;两条线的交叉点就是调度该多快。

### 3. 为什么"少给容量"反而更好

这是全文最反直觉的地方:在信息论上,限制容量应该更差。但它限制的是**早期的**容量——而早期的过度表示本来就是浪费:开头那些 token 里有大量可压缩的冗余(套话、格式、重复),模型在没有压力时会把它们当成重要信息存下来,挤占后面真正需要精确保留的内容。

换句话说:**早期的"宽松"是一种资源错配,不是一种能力。**

## 三、为什么反直觉 / 优雅在哪

- **反直觉**:提升长上下文能力的方法,是**先削弱**它。
- **更反直觉**:在 16K 上(超出 8K 训练窗口、调度早已走完、没有新块可解锁)仍然有增益——说明收益来自**早期压缩得更好**,状态在超长时"退化得更慢",而不是来自"扩容"。
- **优雅**:没有新模块、没有新损失,只是在已有的记忆架构上加一个"块激活日程"。
- **判据**:如果增益只出现在"还有块可解锁"的长度区间,那机制就只是"容量更大";但增益恰恰出现在调度结束后,说明是压缩质量。

## 四、关键证据

**常识推理(平均分)**:

| 模型 | 原版 | +Proteus |
|---|---|---|
| Hope-Attention | 53.15 | **53.99** |
| SWLA | 50.12 | **50.90** |
| Comba | 51.43 | **52.15** |
| Titans | 52.65 | **53.36** |

1.3B 上 Titans+Proteus 拿到表内最好(Wiki PPL 14.94,LAMBADA PPL 13.03,平均 58.00)。

**长上下文检索(16K,NIAH)**:

- Titans:S-NIAH-3 21.4 → **29.8**,S-NIAH-2 69.4 → **74.2**,MK-NIAH-1 11.8 → **16.8**
- Comba:S-NIAH-2 13.4 → **21.2**
- Hope-Attention:MQ-NIAH 30.6 → **34.2**,MV-NIAH 23.0 → **25.8**

**LongBench 平均**:Hope 15.72 → 16.65;Comba 13.05 → 13.23;Titans 13.8 → 14.15。

模式很清楚:**短上下文(已饱和)几乎不动,长上下文 + 难变体涨得最多**。这正是"容量分配"该有的签名。

## 五、边界与可疑处

- 只在 760M / 1.3B 两个尺度;更大模型上"早期瓶颈"是否仍然有益,未知(大模型的早期 token 可能信息密度更高)。
- 调度形状(何时解锁、每次解锁多少)是设计选择,论文没有给出自适应版本;这可能是一个隐藏的超参。
- 需要改架构;对已训练好的模型不能事后加。
- LongBench 的绝对分数很低(13~16),增益虽一致但幅度小,实际意义要打折。
- 我未核对其"块状门控"的实现细节与计算开销(声称无额外成本)。

## 六、对我们有什么用

- **可直接借(思想)**:我们的 Drifting/K 分支如果也维护"一组隐状态/一组专家",同样存在"早期样本霸占容量"的问题。**容量日程**是一个几乎免费的改动:训练早期只激活少量分支,随训练推进逐步放开。
- **可直接借(诊断)**:量一下"记忆/隐状态对各时间位置的敏感度分布"。如果明显偏向开头,说明存在同样的病;这个诊断不需要训练。
- **值得做的小实验**:在我们的条件生成里,把"条件上下文"按时间位置做**递减的容量分配**(早期粗、近期细),看 CRPS 是否改善。时序里"近期更重要"是常识,但"早期该被压缩"不是常识——两者叠加可能有效。
- **只能当反面教材**:别把"记忆越大越好"当默认。固定大小记忆的失败,很多时候是分配问题,不是容量问题。

## 七、值得抄的一句话

> "A key reason is when, not just how, information is written."

> 一个关键原因是信息**什么时候**被写入,而不只是**怎么**写入。
