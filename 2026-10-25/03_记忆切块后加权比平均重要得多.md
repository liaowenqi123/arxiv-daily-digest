# 2026-10-19 · 记忆切块之后,"加权"比"平均"重要得多|Weighted State Souping for Efficient Long-Context Retrieval

> arXiv:2610.25621 · 提交:2026-10-19 · William L. Tong, Aryo Lotfi, Emmanuel Abbe, Josh Susskind, Cengiz Pehlevan, Eran Malach(Apple / Harvard)
> 一句话:把长上下文切成块、各自压成一个状态缓存起来,再用查询相关的权重把它们"调"起来——平均求和会随块数变糊,加权不会。

## 〇、人话版(先看这个)

- **输入**:一堆 token 块(文档、工具定义、记忆记录),每块被 SSM 独立编码成一个固定大小的状态;外加一个查询。
- **输出**:回答(下一个 token)。工程上对应"从一大批缓存块里检索并组合"。
- **任务**:**长上下文检索 / RAG 式问答**,不是分类、不是生成新数据。
- **老问题**:已有的"状态汤"(state souping)把各块状态**直接相加**当初始状态。块少时好用,块一多就糊:SSM 的固定状态本来就做不了精确检索,加进来的每块都在互相干扰。块数超过训练长度后性能直线掉。
- **它改了什么**:给每块一个**查询相关的权重**(类似注意力),按相关性组合,而不是平均;再加一个**稀疏版**:只保留 top-$N$ 块,编码成本接近常数。
- **凭什么更好**:块数增加到训练规模的数倍时,加权版的性能**接近不降**;平均汤和顺序 Mamba 都明显退化;稀疏版在多跳 QA 上甚至**优于**完整 softmax 加权(因为 softmax 权重会摊薄)。用 1.5B Mamba-2 在 SQuAD、HotpotQA、MuSiQue、RULER(NIAH/变量追踪)、BFCL 工具调用上验证。
- **代价**:稀疏版要手设 $N_{top}$(设小了会丢关键块);块边界是硬假设(见下);小 $k$ 时在 BFCL 的 parallel 子集上反而更差,原因未明。
- **类比**:把每本书做成一张索引卡。老办法是把所有卡片**叠在一起**看——书越多,字越糊;新办法是按问题**抽几张最相关的卡**,而且只抽固定张数,所以书再多也不变慢。

**作者核查**:和昨天的《门控》同一组人——Emmanuel Abbe(EPFL)、Cengiz Pehlevan(Harvard)、Eran Malach / Josh Susskind(Apple)、一作 William Tong(Harvard,工作在 Apple)。可信度:**高**。

## 一、它在跟什么较劲

长上下文的两条老路:① 全注意力,贵;② 固定状态 SSM,便宜但检索差。

"状态汤"是一条中间路线:**把长上下文切成块,每块独立编码成一个状态,缓存起来;查询时把这些状态加起来,当作模型的初始状态**,再正常解码。好处是块可以并行编码、可以缓存、可以复用(文档/工具定义变化很慢)。

问题出在"加起来"这个操作:它等价于**不带权重的平均**。块一多,不相关的块也会被加进来,信噪比下降;而 SSM 的固定状态没有"选择性",没法把无关块压掉。于是块数一多,汤就糊了。

## 二、核心思想(机制层)

把"求和"换成"加权求和":

$$s_{\text{init}}(q)=\sum_{i=1}^{k} w_i(q)\,s_i,\qquad w(q)=\mathrm{softmax}\big(f(q,s_1),\dots,f(q,s_k)\big)$$

- $s_i$ 是第 $i$ 块的缓存状态;
- $w_i(q)$ 是一个小网络算出的相关性分数;
- 稀疏版只保留 top-$N_{top}$,其余置零。

**为什么这算"思想"而不是"又一个模块"**:它把"记忆"从**存储问题**改成了**寻址问题**。状态汤的隐含假设是"所有块都该被同等对待";加权版承认"记忆的价值取决于查询",于是同一批缓存可以服务不同问题。

### 理论给出了三条硬边界

- **Proposition 2**:如果每个键值对完整落在**一个块内**,单层足够宽的模型就能做 one-hop 检索(顺序编码和加权汤都可以)。
- **Proposition 3**:如果块边界把键值对**切开**(极端情况:每个 token 一块),那么**没有任何**汤模型能解 one-hop——因为汤对块的**顺序和分组是置换不变的**,切碎后 $C=(k_a,v_u,k_b,v_v)$ 与 $C'=(k_a,v_v,k_b,v_u)$ 会产生同一个状态,而答案不同。
- **Remark 5**:顺序模型可以在深层学会"跨块的压缩表示"(比如把一条链的起点直接连到终点),而独立编码的块做不到——这是汤相对顺序模型的**表达力劣势**。

**如果只能记住一张图**:一条"性能 vs 块数"的曲线。平均汤在 $k$ 超过训练长度后陡降;加权汤基本水平;稀疏加权汤水平且更便宜。

## 三、为什么反直觉 / 优雅在哪

- **反直觉**:提升长上下文能力的办法,不是"更大的状态",而是"更会选择"。状态大小不变,只是决定**谁被加进来**。
- **更反直觉**:稀疏(只看 top-4 / top-20)常常**优于**完整 softmax。因为 softmax 在块多时会把权重摊薄,少量高相关块的信号被稀释——"少看几块"反而更准。
- **优雅**:理论部分只用了一个置换不变性论证(Prop 3),就把"什么情况下汤必然失败"钉死了;不需要复杂假设。
- **判据**:如果块边界切开键值对后性能不降,Prop 3 就错了。作者用"每 token 一块"的极端构造证明了它必然失败。

## 四、关键证据

- **主结果**(Figure 2):块数 $k$ 从 1 增到 128(训练规模数倍),加权汤在 SQuAD / HotpotQA / MuSiQue 上保持接近水平,平均汤与顺序 Mamba 明显下降。
- **NIAH / 变量追踪**:同样的模式;稀疏汤($N_{top}=20$)在难版上保持精度。
- **工具调用(BFCL)**:python simple / parallel 子集表现强;但 small-$k$ 的 parallel multiple 子集反而弱于基线——作者诚实报告,原因未定。
- **效率**:稀疏版编码成本接近常数(与上下文长度无关),因为只需编码被选中的块。
- **理论**:Prop 2/3/4/6 四条,分别给出"能解 / 必然失败 / 多跳可解 / 存储下界 $B\ge m\log_2 N$"。

## 五、边界与可疑处

- **块边界是硬假设**:必须保证键值对不被切开。真实文档/工具定义里,答案经常跨段(表格跨页、函数定义跨文件),这时汤在原理上就会丢信息。
- 稀疏版的 $N_{top}$ 是手设的;设小了丢关键块,设大了退化成稠密。论文把"自适应稀疏"列为未来工作,说明现在没有解法。
- 只在 1.5B Mamba-2 上做;更大模型、混合架构(注意力+SSM)未验证。
- "接近不降"是相对基线,绝对精度仍然不高(图中 EM 只有几十);别把它读成"解决了长上下文"。
- 我未核对附录里每个 benchmark 的具体数字,主结论基于 Figure 2 的趋势。

## 六、对我们有什么用

这条对我们的**检索线**是直接相关的,而且给了一个我们之前没写进文档的硬约束:

- **可直接借(思想)**:"记忆 = 存储 + 寻址"要分开设计。我们之前讨论 RAFT 时,重点是"检索什么";这篇说**检索之后怎么组合**同样决定成败——平均会把候选的差异抹平,加权才能保留选择性。这和"别把分布平均掉"是同一个病理。
- **可直接借(警告)**:**块边界会决定成败**。如果我们的历史窗口按固定长度切块,而关键 pattern 跨块(比如一个 regime 切换跨越切点),检索在原理上就会丢信息。切块应该按**事件/结构**而不是按长度。
- **值得做的小实验**:在我们的检索层,把"top-m 加权平均"换成"top-m 加权求和 + 稀疏选择",看 CRPS/IC 是否改善;同时报告"块边界落在关键 pattern 上的比例",这是免费的诊断。
- **只能当反面教材**:别假设"缓存状态可以无损复用"。置换不变性意味着**顺序信息在汤里是丢的**;如果任务依赖顺序(时序!),这条路线要额外编码位置。

## 七、值得抄的一句话

> "Souping is sensitive to chunk boundaries."

> 汤对块边界是敏感的。
